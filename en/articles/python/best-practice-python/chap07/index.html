Python Unit Testing: Pytest, Mocking, and CI Integration

中 📅 2023-12-13 👁 views this month —

quote

Testing leads to failure. Failure leads to understanding.
The concept of unit testing is likely familiar to most readers. As developers, we write test cases, and the testing framework discovers them, assembles them into test suites, runs them, collects reports, and provides the testing infrastructure (assertions, mocks, setup, and teardown). In Python, the three most popular unit testing frameworks are Pytest, nose, and Unittest, with Unittest being part of the standard library and the other two being third-party tools. The project generated by the `ppw` wizard uses Pytest to drive tests.

Here, we primarily compare Pytest and Unittest. In most cases, choosing one of these two is sufficient. Unittest organizes test cases based on classes, while Pytest is functional, organizing test cases based on modules, and also provides a group concept for organizing test cases. Pytest’s mocking is based on the third-party pytest-mock, which is essentially a simple wrapper around the standard library’s mock. Both frameworks have the concepts of setup and teardown. Unittest uses setUp and tearDown directly as the entry and exit APIs for tests. In Pytest, this is achieved through fixtures, which may have a slightly steeper learning curve. Regarding assertions, Pytest uses Python’s assert keyword, which is more concise than Unittest, although it offers fewer assertion types.

Another notable difference is that Unittest has inherent support for asyncio starting from Python 3.8, whereas Pytest requires the pytest-asyncio plugin. However, there is no significant difference in testing compatibility between the two.

The main advantages of Pytest are:

  1. Pytest test cases are more concise. Since test cases are not production code, developers naturally want to spend less time on them, making code conciseness crucial.
  2. It provides a command-line tool. If we only use Unittest, we must execute unit tests using python -m unittest. With Pytest, we simply call pytest ..
  3. Pytest provides markers, allowing us to more easily decide which cases to execute or skip.
  4. Pytest provides parameterized testing.

Here, we briefly illustrate what parameterized testing is, to help readers understand why it is a noteworthy advantage.

12345678910111213141516171819202122# 示例 7 - 1
import pytest
from datetime import datetime
from src.example import get_time_of_day

@pytest.mark.parametrize(
    "datetime_obj, expect",
    [
        (datetime(2016, 5, 20, 0, 0, 0), "Night"),
        (datetime(2016, 5, 20, 1, 10, 0), "Night"),
        (datetime(2016, 5, 20, 6, 10, 0), "Morning"),
        (datetime(2016, 5, 20, 12, 0, 0), "Afternoon"),
        (datetime(2016, 5, 20, 14, 10, 0), "Afternoon"),
        (datetime(2016, 5, 20, 18, 0, 0), "Evening"),
        (datetime(2016, 5, 20, 19, 10, 0), "Evening"),
    ],
)
def test_get_time_of_day(datetime_obj, expect, mocker):
    mock_now = mocker.patch("src.example.datetime")
    mock_now.now.return_value = datetime_obj

    assert get_time_of_day() == expect​

In this example, we want to test the get_time_of_day method with different time parameters. If we used Unittest, we would need to write a loop to call get_time_of_day() sequentially and compare the results. With Pytest, we only need to use the parametrize decorator to pass an array of parameters (including expected results) for multiple tests. This not only reduces the amount of code but, more importantly, makes the code clearer.

For these reasons, we will primarily use Pytest as the example in the following sections.

1. Organizing Test Code

We generally categorize all test code in a tests folder at the project root. Each test file’s name must either use test_*.py or *_test.py. This is a requirement of the testing framework. Only in this way can the testing framework discover test cases from these files and combine them into suites to be executed when we run commands like pytest tests.

In test_*.py files, function names must also follow a certain pattern, such as test_xxx. Test functions that do not follow the rules will not be executed.

Generally, test files should correspond one-to-one with functional module files. If the code under test has multiple folders, the corresponding test code should be organized in the same directory structure. The purpose is to align business logic with its test code, making it easier to add new test cases and refactor existing ones.

For example, in the sample project generated by ppw, we have:

12345678910
sample
├── sample
│   ├── __init__.py
│   ├── app.py
│   └── cli.py
├── tests
│   ├── __init__.py
│   ├── test_app.py
│   └── test_cli.py

Although there is only one level of directory here, the file names within the directory correspond one-to-one. Note the __init__.py file in this directory. If this file is missing, tests will not become a valid package, causing Pytest to fail to import test cases correctly.

2. PYTEST

Writing test cases with Pytest is straightforward. Suppose sample\app.py is as follows:

123# 示例 7 - 2
def inc(x:int)->int:
    return x + 1

Then our test_app.py only needs the following code to complete the testing:

123456# 示例 7 - 3
import pytest
from sample.app import inc

def test_inc():
    assert inc(3) == 4

This is much more concise than code under Unittest.

2.1. Assembling Test Cases

In Pytest, Pytest searches for test cases in the passed files (or folders) and assembles them into test suites. Additionally, it can use pytest.mark to mark which test cases need to be executed and which need to be skipped.

12345678910111213141516# 示例 7 - 4
import pytest

@pytest.mark.webtest
def test_send_http():
    pass  # perform some webtest test for your app

def test_something_quick():
    pass

def test_another():
    pass

class TestClass:
    def test_method(self):
        pass

We can then choose to execute only the test cases marked as webtest:

1234567891011$ pytest -v -m webtest

cachedir: .pytest_cache
rootdir: /home/sweet/project

test_server.py::test_send_http PASSED                                [100%]

===================== 1 passed, 3 deselected in 0.12s ======================

From the output, it is clear that only test_send_http was executed.

Here, webtest is a custom marker. We can also use Pytest’s built-in markers to filter cases:

  1. pytest.mark.filterwarnings: Adds the filterwarnings marker to test cases to ignore warning messages.
  2. pytest.mark.skip: Adds the skip marker to test cases to skip them.
  3. pytest.mark.skipif: Adds the skipif marker to test cases to skip them based on conditions.
  4. pytest.mark.xfail: In certain conditions (e.g., running on a specific OS), a case might be expected to fail. In this case, this marker should be used to mark it in the test report.

These markers can be viewed using the pytest --markers command.

2.2. Pytest Assertions

During testing, after calling a method, we need to compare its return value with the expected result to determine if the test passes. This is called a test assertion.

Pytest cleverly intercepts and reuses Python’s built-in assert function. Since you have likely encountered assert before, the learning cost for this part is very low.

3. Magical Mocking

During unit testing, we want the testing environment to be as pure and controllable as possible. Therefore, we do not want to depend on user input, nor do we want to connect to exclusive databases or third-party microservices. At this time, we need to use mock to simulate these external interfaces. Mock is possibly the most core technology in unit testing.

Thanks to container technology! In unit testing, more and more databases, caches, and third-party microservices are being connected now. Because the cost of mocking some interfaces has exceeded launching a container, initializing a database, and starting the test.
Both Unittest and Pytest directly or indirectly use the `mock` module from Unittest. Therefore, when you encounter `mock`-related issues, you can consult the [mock](https://docs.python.org/3/library/unittest.mock.html) documentation in Unittest. Our subsequent introduction of `mock` will also focus on the `mock` in Unittest. However, the `mock` in both frameworks shares the same basic concepts.

info

Python only has relatively complete support for `mock` in `async` mode starting from 3.8. Since Python 3.7 has reached the end of its life, this book does not introduce how to implement `mock` in `async` mode in Python 3.7.
The `Unittest.mock` module provides the core `Mock` class. After replacing certain parts of the system under test with an instance of the `Mock` class, we can make assertions about its usage. This includes checking which methods (attributes) were called and whether the parameters passed to them were correct. We can also set return values or cause them to raise exceptions to change the execution path.

In addition, the mock module provides the patch method and the MagicMock subclass. The difference between MagicMock and Mock is that it automatically implements mocking of magic functions in Python class objects (this is the source of its name!). Magic functions refer to functions with double underscores, such as __iter__, etc. patch is a context management tool that automatically restores our changes to the system.

### 3.1. Basic Concepts and Basic Usage

The most basic concept of mock can be demonstrated through the following code:

1234567# 示例 7 - 9
from unittest.mock import MagicMock
thing = ProductionClass()
thing.method = MagicMock(return_value=3)
thing.method(3, 4, 5, key='value')

thing.method.assert_called_with(3, 4, 5, key='value')

This code assumes that we have a class under test, ProductionClass. When we call its method method, there are some inconvenient situations for running under unit testing (e.g., needing to connect to a database). Therefore, we hope to skip calling it and directly return some specified values.

Here, we can obtain a reference to the ProductionClass instance, so we can directly modify its method attribute to point to a MagicMock object. The MagicMock object has some important attributes and methods.

The return_value appearing in line 3 is the first important attribute. It means that when the replaced object (here, method) is called, the return value should be 3. Another similar attribute is side_effect. It also returns the set value when the mock is called. However, there is an important difference between return_value and side_effect: both can be set to arrays (or other iterable objects), but when setting the return value through side_effect, each call to the mock returns the next iteration value in side_effect; whereas return_value only returns the set value all at once. In addition, if both are set, side_effect takes precedence. Please see the following example:

1234567891011# 示例 7 - 10
import unittest.mock

side_effect = [1, 2, unittest.mock.DEFAULT, 4, 5]
m = unittest.mock.Mock(return_value="foo", side_effect=side_effect)

for _ in side_effect:
    print(m())

print(f"m is called by {m.call_count} times")
m.assert_called_with()

The output result will be:

123451
2
foo
4
5

We set 5 values for side_effect. During 5 repeated tests, it sequentially returns the next iteration value. Note that here we use unittest.mock.DEFAULT to let one of the iterations return the set value of return_value. Of course, essentially, this is still an iteration result of side_effect.

Here, another important method appears: assert_called_with, which checks whether the replaced method was called with the expected parameters. In addition, we can also assert the number of times it was called, etc.

3.1.1. Using as a Decorator

Suppose we have a file system-related operation. To test this operation, if we do not use mock, we must build directories and add certain files in the test environment. Unless absolutely necessary, we generally do not want tests to change our file system. This is where we should use mock.

test.test_get_files()

Let us explain the key code. First, when using mock through decorator syntax, our test function will have an additional parameter (here, mocked, but the name can be specified by us). It is also possible to use multiple patch decorators; for each additional decorator, the test function will have one more parameter.

Second, we want to mock Foo.get_files, but we add a __main__ prefix before Foo.get_files. This is because the class Foo is defined in the top-level module. In Python, any symbol (class, method, or variable) exists under a certain module. If this code is saved as a disk file foo.py, the module name is foo; when we import Foo.get_files in other modules, we should use foo.Foo.get_files. But here, since we are referencing within the same module, its prefix is __main__.

info

The key to using `mock` is to find the correct reference method for the object being `mock`ed. In Python, everything is an object. These objects are addressed through hierarchical namespaces. Taking the `patch` method as an example, it is in the `mock` module, and the `mock` module is a subordinate module of the `unittest` package. Therefore, we use `unittest.mock.patch` to reference it, which is consistent with the import path.

However, for scripts like this, if an object is not a system built-in object and does not exist in any package, its namespace is __main__, just like __main__.Foo in this example. Regarding addressing, there are other situations, which we will introduce in the sections on builtin objects and incorrect referencing later.

The `mock` object passed in through decorator syntax has not had its behavior set. Therefore, we must first set its return value here, and then call the business logic function `foo.get_files` -- since it has been `mock`ed, it will return the value we set.

3.2.6. Disappearing Magic

Reiterate: "The key to using mock is to find the correct reference method for the object being mocked." And the key to correct referencing is this "spell":

Warning

Mock an item where it is used, not where it came from.
We illustrate this point with a simple example: 
12345678910from os import system
from unittest import mock
import pytest

def echo():
    system('echo "Hello"')

with mock.patch('os.system', side_effect=[Exception("patched")]) as mocked:
    with pytest.raises(Exception) as e:
        echo()

We call the system’s echo command in the echo method. In testing, we try to mock the os.system method so that it throws an exception as soon as it is called. Then we use Pytest to check: if an exception is thrown, the mock is successful; otherwise, the mock fails.

But if we run this example, we will only get a friendly greeting: "No errors, No warnings!" Why?

Because when we call the system function in the echo() function, at this time, system exists in the __main__ namespace, not the os namespace. The os namespace is where system was born, and the __main__ namespace is where it is used. Therefore, the object we should patch is '__main__.system', not 'os.system'.

Now, let us change os.system to __main__.system and run it again. You will find that the magic works again!

However, more people choose to use the pytest-cov plugin to collect test coverage. This is also the choice of ppw. In projects generated by ppw, pytest-cov has been added to the test dependencies, so it is naturally installed in the environment.

If you want to generate an annotated HTML report, you can use the pytest --cov-report=html command.

By default, coverage.py measures test line (statement) coverage, but through configuration, branch coverage can also be measured. We use the following example code to illustrate what these two types of coverage mean.

123456def my_partial_fn(x):

        y = 10
    return y

my_partial_fn(1)

In the above code, line 2 is an if statement. Depending on the value of x, the next execution may go to line 3 or line 4. When coverage is configured to calculate coverage by statement (which is the default), as long as the function is executed, coverage will count that all statements of the function have been executed; but if coverage is configured to calculate coverage by branch, if the evaluation result of x is False, the code execution will jump directly from line 2 to line 4. Coverage will mark the code from line 2 to line 4 as partially branch covered.

In addition to configuring branch coverage, there are other situations that require configuration. Next, we introduce how to configure them.

The default name of the Coverage.py configuration file is .coveragerc. In projects generated by ppw, this file is located at the project root (readers can return to the end of Chapter 4 to view the file list generated by ppw). If the default configuration file is not used, Coverage.py will read settings from other common configuration files, such as setup.cfg or tox.ini.

In these configuration files, if there is a section with the prefix "coverage:", it will be treated as a configuration for coverage. For example, in .coveragerc, there is a section named run. When it appears in tox.ini, the section name should be [coverage:run].

We can also configure coverage in pyproject.toml. To use this method, we need to add a section named tool.coverage in pyproject.toml, and then add configuration items in this section.

6. TOX for Matrixed Testing

If our software supports 3 operating systems and 4 Python versions, we must create 4 virtual environments on each of the 3 operating systems, install our software and dependencies, and then execute tests and upload test reports. This action is not only quite cumbersome but also prone to errors.

Combining tox with CI can help us automate the creation of these environments and the execution of tests.

6.1. What is Tox?

Tox is a general-purpose Python virtual environment management and testing command-line tool, designed to automate and standardize Python testing. It is part of a larger vision to simplify the packaging, testing, and publishing process of Python software. Most projects use it to ensure software compatibility across multiple Python interpreter versions.

Actually, tox mainly completes the following tasks:

  1. Create Python virtual environments based on multiple versions according to the configuration, and ensure the reproducibility of these virtual environments (requires collaboration with poetry or other dependency management tools).
  2. Run tests and code checking tools in multiple environments, such as pytest, flake8, black, mypy, etc.
  3. Isolate environment variables. tox does not pass any system environment variables to the virtual environment, ensuring the reproducibility of tests.

tip

Beginners may not be accustomed to this feature. This means that if your tests or code need to read certain environment variables, they cannot be set in the host machine running the tests but must be set in the `tox` configuration file. The purpose of this is to ensure the reproducibility of test results.

6.3.1. [tox] Section

Before testing a package, tox first needs to build an sdist distribution package. In terms of packaging, Python has gone through a long journey, and packaging tools and standards have undergone many changes. We will introduce these in a dedicated chapter. Now, we need to know that the latest standards are PEP517 and PEP518, and tox already supports these two standards. However, if the project itself does not support these two PEPs, tox must revert to previous packaging methods.

Therefore, tox introduces the isolated_build option. If set to true, tox will use the PEP517 and PEP518 methods to package the project. If set to false, tox will use traditional methods (setup.py) to package the project. If a project is created through poetry and the requires and build-backend items are set in pyproject.toml, then we need to set isolated_build to true.

In all projects created by ppw, we set isolated_build to true, which is consistent with the settings in pyproject.toml.

The envlist option, as its name suggests, indicates how many environments we need to run tests in. Here, we specified 4 virtual environments: py38, py39, p310, and lint. Tox will automatically determine the Python version to be installed in each environment based on the environment name. For example, it can analyze from the name py38 that Python 3.8 should be used. Here, we also specified a lint environment, which is used to execute code checks. We did not specify a Python version for it specifically. Tox cannot analyze the Python version from the name, so it will use the current Python version.

By default, tox creates a .tox directory in the project root, where the above virtual environments are created:

6.3.2. [testenv] Section

The configuration items in this section apply to all virtual environments. If there are special options and actions in a certain virtual environment, they need to be defined in their own section, such as [testenv:lint].

Here, we also set some extra environment variable fields. For example, we set PYTHONPATH and also ignore some warning messages (line 27). If some of the libraries we use are not updated, a large number of deprecation warnings will be printed during the test process, interfering with our check of error messages during the test. Of course, we should also open this warning at least once in the test to know which usages need to be updated.

Generally, tox will not pass environment variables from the host machine to the test environment. But in some cases, such as account names and passwords for important services, it is not suitable to write them in the configuration file and can only be configured in the host machine’s environment variables. In this case, we need to specify the environment variables to be passed through the passenv option. The value of this option is a comma-separated string, which can be a single environment variable or, as in the example, a wildcard.

Info

In team development, not all developers have access to the account names and passwords of important services. If these secret information items are configured in code files or related configuration files, it will lead to these secrets being exposed to all developers. In addition, if the code repository uses GitLab, it may also lead to these information leaking to the internet. The correct approach is to configure these important information only in the host machine’s environment variables. This way, only those with access to that machine can access these secrets.

This is a standard practice and is also supported by GitHub CI. In GitHub CI, environment variables can be read using the env option in the workflow file, and then passed to the test environment via tox.

The `deps` option declares the Python libraries to be installed in the virtual environment. Different tests may require different dependencies, but in projects generated by `ppw`, we generally only need one common dependency, namely `poetry`. Because the subsequent test commands will all be called through `poetry`.

When Tox installs the package under test, it generally does not install dependencies declared as extra types. However, to run tests and perform lint, we must install third-party libraries such as pytest and Flake8. In projects generated by ppw, these extra type dependencies are further subdivided into dev, test, and doc. Among them, test dependencies are required in all test environments (i.e., py38, py310, etc.), while dev and doc are generally only needed during lint. Therefore, we depend on test in [testenv], while [testenv:lint] depends on dev and doc.

Next is the commands field. This is where tests or lint are actually executed. The command here is:

123commands =
    poetry run pytest -s --cov=%package_under_test% --cov-append --cov-report=xml 
    --cov-report term-missing tests

"-s" tells pytest not to capture console input and output.

In projects generated by ppw, we have already integrated the pytest-coverage plugin. Therefore, through appropriate configuration, we can complete test coverage statistics during testing. --cov is used to indicate the scope of code coverage, where %package_under_test% needs to be replaced with the name of our program library under test. --cov-append indicates that the results of this test will be appended to previous statistics, rather than completely replacing previous data. --cov-report outputs test data in XML format. --cov-report indicates how the report should be generated.

Finally, tests is the folder where our test code is located.
