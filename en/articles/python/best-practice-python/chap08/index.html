Git Version Control Best Practices for Quant Devs

中 📅 2023-12-13 👁 views this month —

1. The Importance of Version Control

When the author was a graduate student, they made a mistake that left a lasting impression. It was 2:00 AM, six hours before our developed system was scheduled to be deployed in a conference room for nearly 20 users—people who would use our software to determine the futures of nearly 10,000 young candidates. At that moment, we discovered that the previously tested and packaged version had been deleted while clearing disk space; however, we had made some code changes after that version. These changes included feature enhancements and minor bug fixes, representing about a day’s worth of work, which had not been tested and could not be released.

Today, programmers might struggle to understand why this was such a major issue. But at the time, due to the lack of version control tools (CVS had only been released a few years prior and had just entered China, so it was understandable that we students were unaware of it), we faced an awkward situation: we had no ready-to-release software, nor a way to easily roll back the code to the version that had passed testing to build an identical release.

It was a painful night. Some began preparing contingency plans, while we, filled with guilt, tried hard to roll back the code as closely as possible to the state of the tested version.

If we had CI/CD, this mistake would almost certainly not have occurred. Even if it did happen, having version control would have significantly reduced the cost of correction.

Version control is a system that records changes to one or more files so that specific revisions can be retrieved later. When writing this book, the author used version control for both the text content and the accompanying source code.

If you are a graphic or web designer, you might need to save all revisions of a specific image or page layout file (perhaps a feature you really desire). Using a Version Control System (VCS) is a wise choice. With it, you can restore selected files to previous states, or even roll back the entire project to a state at a certain point in the past. You can compare detailed changes in files, find out who modified what last, identify the cause of strange issues, determine who caused a feature defect and when, and so on. Using a version control system usually means that even if you mess up the project by modifying or deleting files, you can easily restore the original state, with minimal additional workload.

Back in my graduate school days, many people were accustomed to saving different versions by copying the entire project directory, perhaps adding a backup timestamp to the directory name to distinguish them. The only advantage of this approach was simplicity, but it was particularly prone to errors. Sometimes, one might confuse the working directory, accidentally writing to the wrong file or overwriting an unintended one.

To address this issue, many local version control systems were developed long ago, mostly using some form of simple database to record the differences in file updates. The most popular version control system during this period was likely RCS. Its working principle was to save a patch set on the hard disk (a patch refers to the changes before and after a file revision); by applying all patches, the file content of each version can be recalculated.

The disadvantage of RCS is that it does not support branching operations (we will detail what branching means later), and since it can only manage local files, it cannot support multi-person collaboration. Therefore, Client/Server (C/S) architecture centralized version control systems (Centralized Version Control Systems, CVCS) such as CVS, Subversion, and Perforce were developed. The basic principle of these systems is that there is a single server acting as a centralized file storage and repository, and all files must be accessed through this server, which effectively controls who can do what. The disadvantage of CVCS is that it requires an internet connection to work. If the server is set up in a local area network, it still requires a 24/7 computer as the server, and all files must be accessed through this server, creating a bottleneck in access speed.

To solve these problems, Distributed Version Control Systems (DVCS) such as Git, Mercurial, and Bazaar were developed. The basic principle of DVCS is that every developer’s computer contains a complete version library. When a developer clones a project, they possess the complete historical version of that project. If modifications are made locally and shared with others, one only needs to push the local version library to the server. Afterward, others can pull the latest version from the server to their local machine, merge it with their own modifications, and push it back to the server. This forms a distributed collaborative development model.

In this book, we only introduce Git as the version control system.

2. Version Management Tool: Git

Git was born in 2005, and its developer, Linus Torvalds, is also the creator of the Linux operating system. It has superior performance, is suitable for managing large projects, has an incredible non-linear branch management system, and is currently one of the most popular code management systems in the world.

Git basically continues the concepts and APIs of most version control systems in its interface, but its underlying design is radically different, which has given rise to its powerful engine. Its main features are:

  1. Directly records snapshots, rather than difference comparisons: Other version control systems extract differences between different versions as increments for recording. When extracting the latest file, one must start from the initial version and merge all differences up to the latest version. Early computers had precious storage resources, so previous generations of version control systems adopted this design to reduce storage resource usage. Git, on the other hand, does the opposite: it treats files as snapshots of specific files at a certain moment. Every time you commit an update or save the current state of the project, Git creates a snapshot of all files at that time and saves the index of this snapshot. Git’s design makes it very suitable for handling large projects and is extremely fast.

  2. Almost all operations are executed locally: One of Git’s design goals is to ensure speed. Git’s main operations only require accessing local files and resources, and almost all information can be found locally, so Git is very fast. Another design goal of Git is to reliably handle various non-linear development (branching) histories. Git’s branch and merge operations are very efficient.

  3. Git’s integrity guarantee: All data in Git is checksummed before storage and then referenced by checksum. This means that Git will automatically detect data corruption during storage and transmission.

  4. Append-only operations: The Git operations you perform almost only add data to the Git database. That is, Git almost never performs any operations that could make files unrecoverable. This makes using Git a reassuring and pleasant process, because we know we can freely make various attempts without the danger of messing things up.

Next, we will mainly introduce Git commands and techniques from shallow to deep, following the order of Git usage scenarios.

2.1. Creating a Git Repository

A Git repository (also called a storage repository) is the virtual storage for a project. It allows you to save versions of code, which you can access when needed.

Generally, there are two ways to create a Git repository, depending on how your development work starts. However, before formally introducing them, let’s first look at a basic setup command.

When you first use Git on a machine (or in a project), the first thing we need to do is set your username and email address. This information is used for every commit.

12$ git config --global user.name "John Doe"
$ git config --global user.email johndoe@example.com

Here we used the --global option, so that on the same machine, configuration is only needed once, and all projects will reuse this setting. But if you work on multiple projects simultaneously and want to use different usernames and email addresses for different projects, do not use this option. The result is that these configurations will be written to the .git/config file of the current project, without affecting other projects. Of course, this per-project configuration must be done after the project repository is set up.

Now, let’s create a local repository.

2.1.1. Creating a New Local Repository: git init

To create a new repository, you will use the git init command. git init is a one-time command used during the initial setup of a new repository. When this command is executed, Git will create a new subdirectory in your current working directory. This will also create a new main branch.

This example assumes you already have an existing project folder and want to add it to Git’s version control. We need to enter the root directory of the project first, then run the git init command.

12$ cd /path/to/your/project/root
$ git init

This will create a subdirectory named .git. This subdirectory contains all the necessary files for the Git repository, which is the backbone of the Git repository. However, at this point, we have only performed an initialization operation, and the changes in your project files have not yet been tracked (if we created the repository by cloning from a remote repository, all file changes would already be tracked).

2.1.2. Cloning an Existing Repository: git clone

You may have noticed that the steps to save changes to the Git system are not just one step. To understand these stages, we need to introduce three related basic concepts in depth: HEAD, index, and working tree.

HEAD

HEAD is the pointer to the current branch reference, and it always points to the last commit on that branch. It is also the parent node of the next commit. In some scenarios, we can also regard HEAD as a synonym for the branch. It is where changes go after we execute the git commit command.

Index

When we call the git add command, we record the change in the index area. Then, from here, we commit the change to the branch. More often, people use the term staging area, but index is the standard term used in Git.

Working Tree

Finally, we need to have our own working directory (usually also called the working area). The other two trees (i.e., HEAD and INDEX) store their content in the .git folder in an efficient but not intuitive way. The working directory unpacks them into actual files for editing. You can think of the working directory as a sandbox. You can change it freely before you commit the changes to the staging area and record them in the history.

3. Branch Management

Almost all version control systems support branching in some form. Using branches means that multiple features (or hotfixes) can be developed in parallel; in other words, it can achieve multi-person simultaneous development, or one person simultaneously following up on the development of several features, while the code can still be relatively easily merged in the end.

Some people call Git’s branching model its "killer feature." Because compared to other version management tools, Git’s way of handling branches is incredibly lightweight. Creating a new branch can almost be completed instantly, and switching between different branches is just as convenient. Unlike many other version control systems, Git encourages frequent use of branches and merges in the workflow, even if it is many times a day.

The root cause of Git’s excellent branch management lies in its underlying design. We mentioned earlier that, unlike other software, Git does not save file changes or differences, but a series of file snapshots at different moments. Its feature is to exchange storage space for time (performance).

Until now, we have not given branches a clear and complete definition. We can understand branches this way: Suppose we are developing a blog website. The development group has 4 people, with features such as persistence and caching modules, document object abstraction modules, theme and display modules, comment management modules, etc. If each person is responsible for one feature, the most efficient development mode should be that everyone develops independently on their own branch, completes unit testing for their own modules, and then merges into a common branch (such as called develop) for integration testing. When integration testing is completed, it is merged into the main branch to complete version release, and then enters the next feature iteration.

In addition, we will also encounter such a situation: after the website’s 1.0 version is released, new feature development has already started, but there is an urgent bug that needs to be fixed. At this time, we need to switch to the online branch (i.e., a certain tag on main), create a hotfix branch, fix the bug, test and release, and finally merge it into the main branch and the integration branch (develop).

The above development scenario is a relatively typical one. In 2010, Vincent Driessen abstracted it into a workflow model, which has been widely recognized in the past 10+ years. Bitbucket, a Git version library hosting service produced by the famous Atlassian company, also recommends this model in its official documentation. Vincent also developed the Git extension gitflow based on this model to help people better use this model. So far, this project has received 26.1k stars on GitHub.

{width="50%"}

In this model, there are always two branches on the server, namely the main branch (originally master in the original figure) and the develop branch. The head pointer of the main branch should point to the state when the product build is released, that is, we should be able to build a usable product from the main branch at any time. The develop branch can be regarded as an integration branch; its head pointer should reflect the latest development status of the next release. This is also the branch we use to make nightly builds.

When the code on the develop branch reaches a stable state and is ready to be released, all these changes should be merged into the main branch, and tagged with a version number. By definition, every time a change is merged into the main branch, a new release version should be generated. Therefore, merging into the main branch should be very strict, using hooks to ensure that the CI process automatically builds software and tests, and completes deployment (or publishes to PyPI).

If the developer is a team, obviously, merging from the develop branch to the main branch should be the work of the develop lead.

Besides main and develop, we will also have a series of auxiliary branches, which will only exist temporarily and will eventually be removed. These branches are:

  1. Feature branches
  2. Release branches
  3. Hotfix branches

These branches have their own specific goals, so their sources and final merge destinations also follow strict rules.

3.1. Feature Branch

Feature branches are created from the develop branch to develop a new feature. When the feature development is completed, it needs to be merged back to the develop branch. We can name the branch {{feature_name}}/{{developer}}. Here, feature_name is the name of the feature, and developer is the developer in the team responsible for this feature. Of course, if only one person is responsible for the feature development, the developer part can also be omitted.

We should create a feature branch like this:

1git checkout -b feature_name/developer_name develop

During the development process, we should submit and push changes to the remote server in a timely manner to avoid code loss and facilitate code review by others. When the feature development is completed, we should timely merge the changes from the feature branch back to the develop branch and delete the feature branch. The following is an example of operation commands:

3.2. Release Branch

A release branch is used to prepare a new release, to complete every detail before the official release. This branch also allows small patches and some meta-data changes (such as version number, build date, etc.). Once the release branch is created, the develop branch can continue to develop features for the next version. When the release is completed, it needs to be merged back to the develop branch and the main branch. The branch name generally uses release-*.

The migration from the develop branch to the release branch should occur after all features are merged into develop, and any features not belonging to this release should absolutely not enter the develop branch before this.

The version number should only be determined when the release branch is created. The command to create the release branch is (assuming the previous version is 1.1.5 and the latest version is set to 1.2):

1 files changed, 1 insertions(+), 1 deletions(-)

When the release branch is finally stable and ready to be released, we should merge the release branch into the main branch and create a tag. The name of this tag should be consistent with the version number (generally starting with V). 12$ git branch -d release-1.2

3.3. Hotfix Branch

A hotfix branch is branched from the main branch to fix online bugs. When the fix is completed, it needs to be merged back to the main branch and the develop branch. The branch name generally uses hotfix-*.

The main role of the hotfix branch is to make developers on the develop branch unaffected, while others can quickly fix online bugs. The specific operation commands are similar to the previous examples, so they will not be repeated here. However, it is necessary to remind that we must also assign a version number and create a tag for the hotfix.

If a release branch already exists when performing a hotfix, should the hotfix be merged back to the develop branch or the release branch? The answer is the release branch. If the hotfix is merged into the develop branch, this hotfix will only be released with the next version, which is unreasonable. Therefore, the hotfix should be merged into the release branch, and finally, it will be merged into the develop branch along with the release branch, ensuring it enters subsequent versions.

Compared to not using rebase, after rebase, the branch history will not fork, which can make the branch history clearer.

At this point, we have introduced both rebase and merge for code merging. You must be wondering which method is better, and when to use each method? In fact, no matter which method is used, the final state of the code must be consistent; the difference is only the commit history.

One view holds that the commit history of a repository is a record of what actually happened. It is a document for history and has value in itself, and cannot be changed randomly. From this perspective, changing the commit history is a blasphemy, as you use lies to cover up what actually happened. What if the commit history produced by merge is a mess? Since the fact is so, these traces should be preserved for future generations to check.

Another view is exactly the opposite. They believe that the commit history is what happened during the project process. No one publishes the first draft of a book; software maintenance manuals also need repeated revisions to be convenient to use. People holding this view will use rebase to write the story, writing it in whatever way is convenient for later readers.

Now, let’s return to the previous question: is merge or rebase better? There is no simple answer. Git is a very powerful tool that allows you to do many things to the commit history, but the needs of each team and each project for this are not the same. Since you have learned the usage of both respectively, I believe you can make a wise choice based on the actual situation.

However, we must emphasize that rebase is an advanced operation. Under some complex commit combinations (such as when multiple people collaborate on development and someone rolls back a pushed commit), using rebase may lead to unexpected results. Therefore, before you deeply understand the working principles of rebase, you can also only use merge.

4.3. Branch Comparison: git diff

Git provides the git diff command to compare the differences between two branches. Moreover, it can also compare the differences between two commits. 4.4. Reset and Checkout

We have already encountered the checkout command earlier. Here we introduce another similar command, namely reset.

To understand the reset command, we need to review Git’s three-tree model, namely the working area, staging area (index), and HEAD. The role of the reset command is to point the current branch to a certain commit, while resetting the staging area and working area to make them consistent with the specified commit.

Suppose we have the following commit history:

1234567891011$ git log --oneline
59b6711 (HEAD -> main) test reset
4699b9e (origin/main, develop) Initial commit by ppw

$ git status
git status
On branch main
Your branch is ahead of 'origin/main' by 1 commit.
  (use "git push" to publish your local commits)

nothing to commit, working tree clean

We can see that there is currently 1 unpushed commit, namely 59b6711. Now, we can also reset this commit:

12345678910# 重置到上一个提交。注意，这里的 HEAD~表示上一个提交，我们也可以用提交的 HASH 串
$ git reset --soft HEAD~

$ git status
On branch main
Your branch is up to date with 'origin/main'.

Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
        modified:   README.md

Now, you will see the README.md file appearing under the "Staged Changes" category in the "SOURCE CONTROL" panel of the VSCode sidebar. This is equivalent to canceling the commit operation.

Now we commit README.md again, and then execute the reset command:

1$ git reset --mixed HEAD~

This time, we use the parameter mixed. We will see the README.md file appearing under the "Changes" category, which is equivalent to canceling the commit and add operations.

If we use the --hard parameter to execute reset, then we will also cancel the change of the file itself:

1$ git reset --hard HEAD~

If we do not bring any parameters, reset will execute a mixed operation.

If we execute the reset operation from the graphical interface, it is roughly divided into these steps. First, we find the COMMITS panel, then find the commit to be reset, click it, and select the "undo commit" operation, which is equivalent to executing a "reset --soft HEAD~" operation.

If we also want to cancel the "stage" operation (i.e., undo add), we can find staged changes in the "SOURCE CONTROL" panel, and then click the "unstage all changes" button. The same operation can also be applied to files under the "Changes" category, so we will not repeat it here.

6. GitHub and GitHub CLI

GitHub is an online software source code hosting service platform, using Git as the version control software, written by developers Chris Wanstrath, P. J. Hyett, and Tom Preston-Werner using Ruby on Rails. GitHub started on October 1, 2007, and officially went online in April 2008. In 2018, GitHub was acquired by Microsoft.

Besides allowing individuals and organizations to perform version management, GitHub also provides certain social functions, including allowing tracking (follow) of other users, organizations, and software library dynamics, and commenting on software code changes and bugs. GitHub also provides chart functions to display how developers work on code repositories and the development activity of software.

GitHub CLI can conveniently automate some operations on accounts and repositories. In the project created by ppw, there is a script named repo.sh, which uses GitHub CLI.

In addition, setting some confidential information for repositories through GitHub’s web interface is cumbersome and time-consuming. Suppose you manage more than 10 repositories and need to regularly change these confidential information, it is even more so. We can solve this problem through the gh secret command. The following code is excerpted from repo.sh:

123456789gh secret set PERSONAL_TOKEN --body $GH_TOKEN
gh secret set PYPI_API_TOKEN --body $PYPI_API_TOKEN
gh secret set TEST_PYPI_API_TOKEN --body $TEST_PYPI_API_TOKEN

gh secret set BUILD_NOTIFY_MAIL_SERVER --body $BUILD_NOTIFY_MAIL_SERVER
