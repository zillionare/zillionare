Backtesting requires data spanning long periods. Regardless of the data source, it is impractical to repeatedly transmit large volumes of data across networks while maintaining low latency. Furthermore, as we engage in quantitative research, we gradually build our own factor libraries. The volume of these factor data often exceeds that of the raw data. For instance, using the [TA](https://pypi.org/project/ta/) library, we can extract approximately 86 technical indicator factors at once—ten times the volume of OHLC data at the same frequency. Therefore, how to efficiently store and retrieve this data becomes a significant challenge.

In this series, we will examine several popular technical solutions, including relational databases, time-series databases, file-based storage, column-oriented databases, and distributed solutions. It is difficult to declare an absolute winner; readers should choose based on our evaluation and their specific needs.

## What Data Processing Capabilities Do We Need?
Quantitative data primarily consists of market data (and derived factor data), financial reports (and derived factor data), and trading records. Consequently, it exhibits two main characteristics: massive volume and Point-in-Time (PIT) attributes. Additionally, a complete quantitative system must store trading information, account details, and backtest states.

### Massive Data Volume
Storing quantitative data and providing rapid retrieval may be far more difficult than most people imagine. The primary challenge is the sheer volume of market data. Taking China A-shares as an example, as of December 2023, there are 5,000 listed companies. If we store minute-level market data, we need to save $5000 \times 240 = 1.2$ million records per day. Assuming 250 trading days a year, this reaches 30 million records annually. If we start from the Share Structure Reform in 2005, when there were 1,000 listed companies, and assume a linear increase in the number of listed companies each year, we would need to store $30,000,000 \times 18 \times 0.6 = 324$ million records from 2005 to the present. If we add other frequencies (5-minute, 30-minute), index data, and so on, the total easily exceeds 400 million records.

If we store tick-level data, including bid/ask data (5 levels), the data volume increases by two orders of magnitude.

Clearly, this enters the realm of big data processing. However, if users only need to store daily data and factors at this frequency, the volume is much smaller, and even relational databases can handle it.

Market data has the following read/write characteristics:

1. The vast majority of requests are reads.
2. Write requests (can) be updated in large batches (>1,000 rows) or not at all.
3. Data already added to the database generally does not require modification (unless there are data errors).
4. Reads often involve many rows but extract only a small subset of columns.
5. Wide tables (considering the join between market data and factors).
6. Column data is relatively small, either numeric or short strings.
7. Queries must be as fast as possible.

As we will see later, some storage solutions are almost custom-built to meet these requirements.

### PIT Attributes
PIT stands for Point-in-Time Data. Some economic data is often revised after its initial release, such as macroeconomic data like GDP or corporate financial reports. Taking corporate financial reports as an example: if a company releases its Q1 2021 report (version 1.0) at the end of Q1, and revises the Q1 report during the semi-annual report release, the Q1 report version becomes 2.0. If the data source records the data version and its generation time (not just the attribution time) at the time of release, this data is called Point-in-Time (PIT) data.

If using a relational database, storing data with timestamps is not an issue. For file-based storage, appropriate indexing methods must be considered to preserve PIT attributes.

## Zillionare 2.0’s Data Storage Strategy

Regardless of the underlying technology, we generally adopt a cache + persistence strategy. In Zillionare 2.0, today’s market data is stored in cache, offering fast update and query speeds but limited capacity. Additionally, some data synthesis is required. For example, to query a specific asset’s daily data for the past 250 days, we must first extract 249 days of market data from persistent storage and add today’s data stored in Redis—which updates every second. Omicron synthesizes this data before returning it to ensure the user receives a complete dataset.

Zillionare 2.0 uses Redis 7.0 for caching and InfluxDB for persistent storage—the premier time-series database.

Zillionare acquires minute-level data and real-time price data (approximately every 5 seconds, excluding open/high/low, containing only the current price) from upstream sources. Omicron provides 5-minute, 15-minute, 30-minute, and 60-minute data. Therefore, when Zillionare receives minute-level data from upstream and saves it to Redis, we must use the latest minute-level data to synthesize 5-minute, 15-minute, 30-minute, and 60-minute data, as well as the daily data for the current day. This workload is much larger than imagined. In fact, it runs every 5 minutes. Considering we have 6,000 assets, this requires executing 30,000 resampling tasks at once during the convergence points of 5, 15, 30, and 60 minutes—and it must be completed within seconds.

We leveraged a new feature in Redis 7.0: server-side Lua scripts, to execute this synthesis task. Relying on Python would have been too slow; using Lua is key to completing this task in time. This eliminates grid transmission time, and Lua runs significantly faster than Python—essentially at C-speed.
