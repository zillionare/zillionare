Backtesting requires data spanning long periods. Regardless of the data source, it is impractical to repeatedly transfer large volumes of data across networks while maintaining low latency. Furthermore, during quantitative research, we gradually accumulate our own factor libraries. The volume of these factor data can even exceed that of the raw data. For instance, using the [TA](https://pypi.org/project/ta/) library, we can extract approximately 86 technical indicator factors in one go—ten times the volume of OHLC data at the same frequency. Therefore, how to store and retrieve this data efficiently becomes a significant challenge.

In this series, we will examine several popular technical solutions, including relational databases, time-series databases, file-based storage, column-oriented databases, and distributed solutions. It is difficult to declare a single absolute winner; readers should select based on our evaluation and their specific needs.

## What Data Processing Capabilities Do We Need?
Quantitative data primarily consists of market data (and derived factor data), financial reports (and derived factor data), and trading records. Consequently, it exhibits the characteristics of massive scale and Point-in-Time (PIT) attributes. Additionally, a complete quantitative system must store trading information, account details, and backtest states.

### Massive Data Scale
Storing quantitative data and providing fast retrieval may be far more challenging than most people imagine. The first hurdle is the sheer volume of market data. Taking China A-shares as an example, as of December 2023, there are 5,000 listed companies. If we store minute-level market data, we need to save $5000 * 240 = 1.2$ million records per day. Assuming 250 trading days a year, this reaches 30 million records annually. If we start from the Share Structure Reform in 2005, with 1,000 listed companies, and assume a linear increase in listings each year, we would need to store $30,000,000 * 18 * 0.6 = 324$ million records from 2005 to the present. Including 5-minute, 30-minute, and other data frequencies, plus index data, this easily exceeds 400 million records.

If we store tick-level data, including bid and ask data (5 levels), the data volume increases by two more orders of magnitude.

Clearly, this enters the realm of big data processing. However, if users only need to store daily data and factors at this frequency, the volume is much smaller, and even relational databases can handle it.

Market data has the following read/write characteristics:

1. The vast majority of requests are reads.
2. Write requests (can) be updated in large batches (>1,000 rows) or not at all.
3. Data already added to the database generally does not require modification (unless there is an error).
4. Reads often involve fetching many rows but extracting only a small subset of columns.
5. Wide tables (considering the join between market data and factors).
6. Column data is relatively small, either numeric or short strings.
7. Queries must be as fast as possible.

As we will see later, some storage solutions are almost entirely customized to meet these requirements.

### PIT Attributes
PIT stands for Point-in-Time Data. Some economic data, such as macroeconomic data like GDP or corporate financial statements, are often revised after initial publication. Taking corporate financial reports as an example, if a company released Q1 2021 report version 1.0 at the end of Q1, and revised the Q1 report during the semi-annual release, the Q1 report version should become 2.0. If the data source records the data version and its generation time (not just the attribution time) upon publication, this data is referred to as Point-in-Time (PIT) data.

If using a relational database, storing data with timestamps is not an issue. For file-based storage, however, appropriate indexing methods must be considered to preserve PIT attributes.

## Zillionare 2.0 Data Storage Solution

Regardless of the underlying technology, we generally adopt a cache + persistence strategy. In Zillionare 2.0, today’s market data is stored in cache, ensuring fast updates and queries, though with limited capacity. Additionally, some data synthesis is required. For example, to query the past 250 days of daily data for a specific asset, we must first extract 249 days of market data from persistent storage and add the current day’s data stored in Redis—which updates every second. Omicron synthesizes this data before returning it to the user, ensuring the delivered data is complete.

Zillionare 2.0 uses Redis 7.0 for caching and InfluxDB for persistent storage—the premier time-series database.

Zillionare acquires minute-level data and real-time price data (approximately every 5 seconds, excluding open, high, low, and containing only the current price) from upstream sources. Omicron provides 5-minute, 15-minute, 30-minute, and 60-minute data. Therefore, when Zillionare receives minute-level data from upstream sources and saves it to Redis, we must use the latest minute-level data to synthesize 5-minute, 15-minute, 30-minute, and 60-minute data, as well as the daily data for the current day. This task is much larger than imagined. In fact, it runs every 5 minutes. Considering we have 6,000 assets, at the aggregation points for 5, 15, 30, and 60 minutes, we must execute 30,000 resampling tasks at once—and complete them within seconds.

We leverage a new feature in Redis 7.0: server-side Lua scripts, to execute this synthesis task. Relying on Python would not allow this task to complete in time. This approach saves grid transmission time, and Lua is significantly faster than Python—it essentially runs at C speeds.
