Zillionare (Da Fu Weng) is a distributed, high-speed quantitative trading framework. Built on Python 3.8+ and leveraging asynchronous I/O and microservices, its goals are:

- A distributed, high-speed quantitative computing platform with seamless, scalable compute power.
- Localized market data storage with low-latency synchronization, easily supporting real-time triggering of minute-level or higher trading signals.
- Support for private deployment to protect your strategies.
- Virtualized deployment for easier maintenance.
- A wide range of quantitative factors.
- Machine learning-based trading strategies.
- Deep learning-based trading strategies.
- A high-speed backtesting framework.

# **Why Develop Zillionare?**

The author began focusing on quantitative trading in 2019. After testing various commercial and open-source products, the author found that no product could provide low-latency, accurate data at an affordable cost, particularly in the realm of machine learning and deep learning-based trading strategies.

Some products excel in data source organization and reliability but do not offer offline storage. If every data point must be fetched online, this creates issues with data request response speed and costs.

**Slow Data Request Response Speed**

???+ Info
    Our strategies often require scanning the entire market to discover trading signals as comprehensively as possible. However, this leads to a massive volume of data requests.

    Take a moving average strategy as an example. Assuming the strategy uses annual line data, scanning the entire market would require fetching 1 million data points from the server in one go (based on ~4,000 China A-share targets, with a maximum of 250 days of annual line data per target).

    Fetching such a large volume of data involves an astonishing number of network requests and time consumption. For instance, using a certain SDK, fetching 1 million data points in a single session typically takes 7–10 hours. Consequently, implementing any real-time or near-real-time trading strategy becomes impossible. Even in non-real-time scenarios, such as database initialization after initial installation, the wait time for some open-source projects can span days (even with breakpoint support), which is unacceptable.

**Cost**

???+ Info

    Fetching all data from the server imposes a significant load, meaning services cannot be provided for free.

    For example, JoinQuant is an excellent data provider. Users can apply for a one-year free trial, which provides 1 million data points (requests) per day. While this scheme is generous, it is insufficient even for independent research, let alone production environments. The author often encounters situations where the quota is exhausted before a single unit test cycle completes.

    The fundamental solution to these issues is to store closed K-line data locally and synchronize differential data between the local environment and the upstream server in real time.

    Some products offer similar local data storage solutions, but they come with limitations and defects.

    For instance, some products divide data-fetching APIs into offline and online categories. Using the offline API allows reading from local storage, but the data is not real-time and cannot guide real-time trading. To obtain real-time data, one must still use the online API, either by fetching all required data at once (negating the advantage of local storage) or by fetching differential data via the online API and manually merging it with offline data from the database. In reality, the product should transparently provide the data users need, hiding these technical details internally, allowing users to focus more on strategy development.

**Technical Debt**

???+ Info

    From a technical perspective, the Python community has progressed significantly. Some products started early and locked their architecture into outdated tech stacks, creating technical debt.

    Users of quantitative trading frameworks often need to perform secondary development. During this process, they inadvertently lock their own tech stacks into these outdated technologies, which is unfair to secondary developers.

    For example, some products use synchronous I/O for both reading local data (from databases) and remote data. For applications developed in Python, this is a severe performance design flaw. The limited computing resources Python can leverage are often consumed by IO waits.

**Quality Control**

???+ Info

    The quality control of some commercial projects is hard to assess. However, even for open-source projects, if CI is not used and there are no test coverage reports, assessing quality control is difficult despite the code being open.

Therefore, the author decided to develop a framework dedicated to addressing these issues and introducing machine learning and deep learning into trading strategies.

Of course, due to limitations in personal technical skills and vision, Zillionare undoubtedly has various shortcomings. Whether it meets the author's expectations also depends on user feedback.

# **What Are Zillionare's Technical Features?**

**High Performance**
    To ensure Zillionare's high performance, the author engaged in deep thinking regarding architecture, component selection, algorithms, and data structures, making trade-offs from a product positioning perspective.

???+ Info    
    Zillionare's architecture utilizes multi-process, distributed microservices, message queues, load balancing, and caching (in-memory) databases. For market data synchronization (both real-time and non-real-time), it employs a multi-process collaboration mode, significantly increasing network concurrency. In terms of process collaboration, it supports both load balancing modes (via Nginx) and parallel modes (supported by built-in messaging mechanisms).
    
    Network components are chosen to support asynchronous I/O wherever possible. For example, `aioredis` is used for accessing Redis databases, and `asyncpg` is used for database access.
    
    After in-depth research into the primary data type—market data—and considering its distribution and processing characteristics, we decided to use Redis for persistent storage of market data and Numpy structured arrays for in-memory representation of market data (other frameworks generally use Pandas).     Additionally, we continuously optimize from an operational perspective. For example, data import after initial installation, leveraging CDN acceleration and multi-process modes, takes only 170–240 seconds to import one year of China A-share data (including 30-minute and higher K-lines) in Zillionare (depending on your CPU cores and network bandwidth). If sufficient CPU cores are available, importing several years of data takes approximately 15–20 minutes (in testing, importing 70 months of data took only 776 seconds using 32 processes). These figures will continue to be optimized to achieve good speeds even on lower-spec computers. Users who have used other products may have a deeper appreciation of Zillionare's speed.

**Ease of Use and Quality Control** 
    Before the 1.0 release, Zillionare's two most critical early components underwent multiple rewrites to ensure proper decoupling and aggregation of functions, guaranteeing API stability and readability.
???+ Info

    If you have the opportunity to delve into Zillionare's development toolchain, you will find that quality control occurs at every stage, from code submission and unit testing to continuous integration.

    For deployment, we support both virtualized deployment and pip installation. Virtualized deployment is fully automated with one click, while the pip installation mode provides an installation wizard to guide users through configuration after installation, making the entire process straightforward.

**Keeping Pace with Community Latest Technologies**

???+ Info
    Initially, Zillionare used the `cookie-cutter` pyproject template to build its development framework. This template used Makefiles, pip, and requirements files to manage dependencies and build the project, `twine` for publishing, and tools like `tox` and `pytest` for quality control, with `Sphinx` for documentation.
    
    In dependency management, we observed the community migrating toward new standards and tools. For example, Poetry, which fully complies with PEP 517, has become the community's preferred tool for dependency, build, and version management. Therefore, Zillionare completely replaced its build framework last November.
    
    Documentation tools were also switched to `mkdocs` to reflect the reality that Markdown format is preferred by both authors and readers.

    Additionally, we integrated Travis CI and Codecov for continuous integration. We use `pre-commit-hooks` to ensure the quality of committed code. Before the 1.0 release, this test coverage reached 93%.

    Going forward, Zillionare will maintain this technical positioning and strive for more standardized project releases. We will determine project directions via RFCs, define API interfaces, and ensure interface usability through technical testing coverage.


**AI-Oriented Design** 

???+ Info

    Although Zillionare's AI features are still under implementation, our design fully reflects an AI-first orientation. For instance, our design prioritizes momentum strategies, while paying less attention to text and financial data. This is because AI is not yet particularly reliable in text analysis, and trading based on news lacks certainty. Financial data faces similar issues. Currently, AI performs best in momentum strategies, which is why this is Zillionare's focus.

    Regarding quantitative factors, we do not view them, as traditional financial engineering might, as simple combinations that lay golden eggs. Instead, we treat them primarily as data preprocessing and feature extraction for machine learning and deep learning. This also reflects our AI-oriented design philosophy, which I believe is the correct approach.

# **Who Is Zillionare For?**

1. Zillionare is positioned to provide quantitative trading tools and strategies for the China A-share market, with a focus on momentum strategies. There are currently no plans to integrate futures or cryptocurrencies.
2. High-frequency arbitrage trading is not Zillionare's focus area—this field relies more on hardware and network speed, or fundamentally, on capital; algorithms and strategies may not be dominant here. Zillionare is positioned to serve the complex China A-share market, bringing open-source AI technology to it. Zillionare's architecture is designed to handle market data at the minute level or higher. While deep learning on Tick-level data has its merits, this field should primarily focus on arbitrage trading.
3. The historical market data provided by Zillionare starts from 2015 and currently includes all stocks' data at 30-minute intervals and higher.
4. Users of quantitative trading frameworks often have secondary development needs. Zillionare's advanced and standardized tech stack ensures that users' investments remain effective for a long time in the future.
5. From a tech stack perspective, Zillionare is developed purely in Python. The operating system is limited to Ubuntu > 18. Users unfamiliar with this OS can deploy it using our containerized deployment method.

Compared to other products, Zillionare's feature set is relatively tight. We prefer to remain focused and concentrate on doing things well.
